# カメラ方式：実装した検証範囲

Windowsは使わず、Pi 5と2台のCamera Module 3 Wideで完結する構成。
今回のソフトにはGPIO出力が存在しない。旧PCB設計と旧Webシミュレータは変更しない。

## 処理の流れ

Picamera2の2撮影スレッド → 各1枚だけの最新フレーム → 輝度画像・線路ROI → 固定背景差分と局所追跡 → 撮影時刻に基づくA/B横断 → 進路の模擬要求。
Pi内のブラウザには640×360・4fps程度のプレビューを表示し、1080p2本を常時圧縮する負荷を避ける。
main1920×1080、lores1280×720、15fpsを初期設定にしているが、実Piでの性能保証値ではない。
センサモードは候補内の最大クロップ面積を優先し、使用モードと画角を記録する。被写体・レンズ歪み・ピントは撮影後に確認。

## 進路選択

- Aは待機開始だけで、ポイント要求を出さない。
- 時間差方式は同一追跡IDがA→Bへ到達した時間で選択。
- LED方式はBを撮影した時点の位相で選択。処理完了や画面更新の時刻で選ばない。
- Bで確定しても実出力はせず、模擬要求を記録する。
- 編成全体の通過を運転者が確認するまでロック。解除で直進へ戻したり、前回要求を再送したりしない。
- 見失い・曖昧な対応・撮影停止・処理一時停止では、新しい要求を保留する。空線を推定しない。
- 車両の停車・発車は手動。

## 今回の追跡の限界

4個の模擬車両を同時検出できる試作。実車4編成の識別や、複数車体を1編成へまとめる性能は未検証。
IDは担当カメラ／検知範囲内での一時ID。カメラ間のID引継ぎ、全線を1周する永久IDは実装していない。
各A/B地点を1台のカメラが担当する。AとBを別カメラへ分割して同一IDとみなすことはできない。
検知基準は検出領域の中心であり、実際の先頭・最後尾の位置ではない。A/B位置とポイントまでの余裕は実車で調整する。
線路が交差して見えても画像から接続を推測しない。各接近区間のROIを独立登録し、投影ROIが重なって識別不明なら判定保留。

背景は列車のない画像を手動で登録する。通常フレームで学習更新しないので、停止車両を背景に吸収しない。
照明変化・影・パンタグラフ・建物・架線柱による誤検出や遮蔽は実映像で評価する。
ライブの再登録で追跡の連続性がなくなるため、進路待機中／確定中のチャンネルは保留状態になる。

## 時刻と遅延

PiではSensorTimestampと同じ起動時刻基準を使用する。取得時刻と現在時刻が大きく違う場合は映像を受け入れない。
デモは同じ基準の模擬時刻、録画はFPSから作る再生時刻。録画ファイルに撮影時の正確な時刻を復元したものではない。
フレーム落ち・処理時間・撮影からの経過時間を記録。UIの表示LEDと実LEDのタイミング一致はまだ測定していない。
ポイントへの接近距離は「最高速度×撮影・処理・通信・転換の総遅延＋位置の余裕」で決める。

## 実機出力へ進む前の設計事項

Pi5のGPIOでコイルを直接駆動しない。Hブリッジと独立したハードウェアパルス制限が必要。
画像処理とGPIOを別プロセスにするだけでは、Linux停止時の連続通電を防げない。
旧基板を再採用するか、新しい市販回路／別回路を使うかは今回確定していない。
